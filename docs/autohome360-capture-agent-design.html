01五个关键设计判断

在动手之前，有五个判断决定了整个系统的走向。它们比任何一行代码都重要，方向错了后面全是返工。

判断一
不录坐标，录语义
传统宏录制记的是"在 (742, 381) 点一下"，页面一改版、分辨率一变就全废。本方案记的是"点了文案为『中控』的机位按钮，之后画面从 A 状态变成 B 状态"。回放时用多候选选择器重新定位，用状态变化校验结果。
判断二
视角是隐藏状态，必须靠图像确认
360° 全景是 WebGL canvas 渲染，视角不在 DOM 里。你有三条路：直接读渲染引擎的 camera 对象（最准）、读页面上的机位按钮激活态（次之）、比对像素（永远可用的兜底）。系统要能自动在这三条之间降级。
判断三
"大概到了"不算到位
拖拽调视角天然有误差，累积几次就偏了。必须用闭环：截图 → 与基准图算特征点匹配 → 估算还差多少像素 → 再拖 → 再比。这是控制论里的视觉伺服（visual servoing），是本方案的技术灵魂。
判断四
去标识是法律问题，不是技术问题
技术上擦掉一个水印很容易，但那属于侵犯署名权、违反网站协议的高风险动作。本方案把"去标识"设计成需要授权令牌才能开启的模块，默认关闭，并给出四条合规替代路径。
判断五
先花半天做可行性探测，再写代码
如果目标页面把 camera 对象暴露在 window 上，整个方案难度降一个数量级；如果机位全部是预设按钮，那就简单到不像话；如果只能纯拖拽且画面有随机噪声，方案复杂度会翻倍。这三种情况的工程量差 5 倍以上。P0 阶段必须先回答这个问题，再决定投入。

02整体架构与模块划分

系统分左右两半：左边"学一次"，右边"跑一万次"。中间的任务描述文件是唯一的契约——它是录制的产物，也是执行的输入。

模块清单与职责

模块类型职责关键输入 / 输出
Recorder
录制器		一次性 在人工演示过程中，同步采集四类信号：键鼠事件流（含时间戳与坐标）、DOM 快照（每次交互后的元素路径/属性/可见性/包围盒）、canvas 帧采样（每 200ms 或每次交互后）、网络请求（XHR/WebSocket，用于识别数据接口）。同时注入脚本探测 window 上是否暴露了渲染引擎的 camera 对象。 入：人工操作
出：raw_trajectory.jsonl
Abstractor
抽象器		一次性 把原始轨迹"清洗成人话"：① 去噪——删掉误点、合并连续 mousemove 成一个 drag 动作；② 生成鲁棒选择器——对每个被操作元素产出 4 层候选并按稳定性打分；③ 抽取变量——识别出哪些字符串随车型变化（URL、配色名、机位名）；④ 推导等待条件——从"这次等了 3.2 秒画面才出来"反推出应等待的条件（帧稳定 / 元素出现）。 入：原始轨迹
出：task.yaml
StateProbe
状态探测		运行时 决定"怎么确认到位"。三级通道自动降级：L0 直接读 camera 的 yaw/pitch/fov（误差 <1.5° 即通过，最快最准）；L1 读 DOM 语义（激活按钮文本、URL hash）；L2 像素比对（永远可用）。运行时逐条尝试，记录当前生效的通道。 出：当前校验通道等级
Runner
执行器		批量 单任务状态机。支持 8 种原子动作：navigate / click / drag / wheel / select / wait / screenshot / assert。每步执行遵循固定节奏：定位 → 前置校验 → 动作 → 显式等待 → 后置校验 → 判定。拒绝使用 sleep(3000) 这类固定等待，一律用条件等待。 出：原始截图 + 步骤轨迹
Aligner
视觉伺服对齐		核心 把"大概到了"收敛到"精确到位"。迭代循环：截图 → 与基准图做 ORB 特征点匹配 → RANSAC 估计单应矩阵 → 换算成还需拖拽的像素量与方向 → 执行小步拖拽 → 重新截图比对。收敛条件：SSIM ≥ 阈值 或 特征内点率达标 或 位移落入死区（<2px）。最多 6 轮，超预算则回全景原点重来。 入：当前帧 + 基准图
出：对齐后的画面
Verifier
校验器		核心 两道关。前置：页面版本指纹——对 DOM 骨架算 hash，与录制时比对，变了说明改版，立刻停止并告警（不是重试能解决的问题）。后置：与基准图算 SSIM + pHash，判定 PASS / RETRY / DEGRADE / FAIL。 出：判定结果 + 相似度数值
PostProcessor
后处理链		批量 可插拔流水线，每个模块实现统一接口 (image, ctx) → image，独立开关、顺序可调。内置：裁剪 / 缩放 / 色彩归一化 / 锐化 / 质量分级 / 来源处理 / 导出。其中"来源处理"模块带合规强制门槛。 入：原始截图
出：成品图 + 评分
Naming & Storage
命名与存储		批量 模板引擎渲染文件名与目录层级；两级去重（pHash 快筛 + SHA256 确认）；SQLite manifest 记录每条任务状态，支撑断点续跑；失败清单输出 CSV + JSON。 出：成品库 + 状态库 + 报告
Scheduler & Limiter
调度与限流		批量 并发上下文数控制（WebGL 上下文有浏览器级上限，建议 ≤4）；动作间与车型间的随机抖动延迟；指数退避；日配额熔断；触发 captcha / 403 / 429 时全局停止。 出：任务队列节拍
ComplianceGate
合规闸门		强制 独立于业务逻辑的硬门槛。校验 license_ref、mode、attribution 三项配置，决定后处理链中哪些模块允许启用。任何试图绕过授权的调用都会被拒绝并记录审计日志。 出：放行 / 拒绝 + 审计
Observability
可观测性		支撑 每次运行生成证据包：原始截图、对齐迭代过程图、相似度数值曲线、步骤耗时、失败现场。出问题时不靠猜，靠证据包复现。 出：evidence/{run_id}/

选择器为什么需要 4 层候选

页面上的元素不会一直用同一个 class。稳妥的做法是按抗变更能力排序，运行时依次尝试，全挂了再走视觉锚点兜底：

L1 埋点属性 [data-track='360-interior'] — 为数据而加，最不容易被UI重构误删
L2 语义属性 [aria-label='进入全景'] / [title=...] — 兼顾无障碍，变更频率低
L3 可见文本 text=中控 / :has-text('中控') — 会随文案改版变，但可读性好
L4 结构路径 .pano-wrap > .nav > li:nth-child(2) — 最脆，仅作兜底
L5 视觉锚点 在基准图上标注元素区域，用模板匹配定位 — 改版后最后的救命稻草

04机位字典：本方案真正的设计资产

这一节是给你的。前面讲的都是工程，但决定这套东西有没有专业价值的，是机位字典做得好不好。

为什么机位字典比 Agent 本身更重要

一个能自动截 500 张图的工具不值钱——截出来的图如果角度随机、光照不一、构图混乱，对 Benchmark 毫无意义，甚至会误导判断。真正值钱的是一套跨车型严格可比的标准化机位定义：同样是"中控正视"，理想 L9 和宝马 i3 截出来的必须是同一个观察关系，才能横向比 IP 分缝、屏幕占比、出风口节奏。

所以机位字典必须由你来定义，工程只是让它在几百台车上被忠实执行。

每个机位需要定义三层

层次回答什么问题示例（V02 中控正视）
semantic
语义层		这个机位要表达什么设计信息？做横向对比时看什么？ 正对仪表板，横向对称；用于比较 IP 分缝、出风口形式、屏幕宽高比与厚度感
acquire
获取层		怎么到达这个机位？是点预设按钮还是拖拽？ 优先点文案为"中控"的预设按钮；若无预设，则用基准图 V02_ip_front.png 做视觉伺服对齐
verify
校验层		怎么确认到位？容差多少？ SSIM ≥ 0.92、pHash 汉明距离 ≤ 6；若可读 camera 则 yaw/pitch 偏差 < 1.5°

一个容易被忽略的细节：机位顺序

拖拽式机位会有误差累积——从 A 拖到 B 再拖到 C，每一步的残差会叠加，越往后偏得越多。解决办法是定义一条执行路线：每个车型都先回到全景（V08）作为原点，再从原点出发去各个机位，把累积误差清零。配置文件 views.yaml 里的 default_route 就是干这个的。

任务描述文件的骨架（最关键的一份）

# 1. 参数声明 —— 由 targets.csv 列名绑定
params:
  - { name: brand,     type: string, required: true }
  - { name: model_url, type: url,    required: true }
  - { name: color,     type: string, required: true, default: "默认" }
  - { name: view_id,   type: string, required: true, ref: "views.yaml" }

# 2. 状态探测 —— 决定"怎么确认到位"，三级自动降级
state_probe:
  camera_hook: { enabled: true, candidates: ["window.__viewer?.camera", ...], tolerance_deg: 1.5 }
  dom_state:   { enabled: true, sources: [".view-tab.active::text", "location.hash"] }
  pixel_fallback: { enabled: true }

# 3. 步骤序列 —— 每步都是"定位 + 动作 + 等待 + 校验"四件套
steps:
  - id: open
    action: navigate
    url: "{{model_url}}"
    settle: [ {type: network_idle, duration_ms: 800} ]
    post_check:
      - { type: page_version, expected: "{{fingerprint}}", on_mismatch: abort_and_alert }

  - id: wait_pano_ready              # 最容易失败的一步，给足预算
    action: wait
    conditions:
      - { type: canvas_stable, frame_diff_threshold: 0.004, consecutive_frames: 3, timeout_ms: 45000 }
    on_timeout: [ {action: reload_once, then: retry}, {action: degrade, to: low_res_mode}, {action: fail_record} ]

  - id: align                        # 视觉伺服闭环，方案核心
    action: align
    baseline: "baselines/{{view_id}}.png"
    max_iterations: 6
    convergence: { ssim_min: 0.90, phash_max: 8, camera_delta_deg: 1.5 }
    deadzone_px: 2
    on_not_converged: [ {action: reset_to_view, view_id: V08_overall, then: retry_align}, {action: fail_record} ]

  - id: capture
    action: screenshot
    pre_actions:                     # 截图前"冻结"画面，保证可复现
      - { action: hide, selectors: [".tooltip", ".share-bar"] }
      - { action: move_mouse_to, x: -10, y: -10 }   # 鼠标移出，避免 hover 高亮
      - { action: pause_animations, value: true }
    filename: "{{brand}}_{{series}}_{{color}}_{{view_id}}_{{seq}}"
    post_check: [ {type: image_not_blank}, {type: verify_against, baseline: ..., ssim_min: 0.90} ]

# 4. 全局兜底 —— 出现这些情况不是重试能解决的，要停
guards:
  on_captcha: stop_all_and_alert
  on_login_required: stop_and_alert
  on_http_429: { action: backoff, multiplier: 4, then: continue }
  on_page_version_mismatch: stop_all_and_alert

06核心难点：视觉伺服对齐

这是整个方案唯一有真正技术含量的地方，也是决定"能不能用"的分水岭。

问题的本质

你演示时把视角拖到了某个位置，系统记下"拖了 (dx=-312, dy=+47) 像素"。但这个数字不能直接用——因为拖拽量与角度变化的关系是非线性的：画面边缘和中心的灵敏度不同，不同车型的全景球体半径不同，鼠标加速度曲线也会干扰。更糟的是误差会累积。

所以必须用闭环：不预测"该拖多少"，而是看当前画面与基准图差多少，边看边修。这就是机器人领域的视觉伺服。

几个必须想清楚的实现细节

  • 死区（dead zone）不能省。位移小于 2px 时必须判定收敛并停止，否则系统会在目标附近来回抖动，永远不收敛，白耗时间。
  • 迭代轮次要设预算。最多 6 轮、总时长 60 秒。超预算不要硬扛，回全景原点重新开始——大概率是粗调阶段就跑偏了，继续微调没意义。
  • 特征匹配会失效。如果画面是纯色顶棚、反光玻璃这类弱纹理区域，ORB 找不到足够特征点。此时要降级：改用相位相关（phase correlation）估整体平移，或者干脆只用 SSIM 做爬山搜索（慢但稳）。
  • 阈值不能拍脑袋定。正确做法是标定：拿同一车型同一机位重复截 10 次，算它们之间的 SSIM 分布 → 得到类内方差；再拿同一车型不同机位的图互相比 → 得到类间方差。阈值取两者之间。不同机位的纹理丰富度不同，阈值应该逐机位标定，而不是全局一个值。这也解释了为什么 views.yaml 里每个机位有各自的 tolerance_ssim。
  • 能读到 camera 就别用视觉。如果 L0 通道可用（能读 yaw/pitch），对齐就退化成一个简单的数值收敛问题，几十毫秒就能到位，且完全精确。视觉伺服只在 L0/L1 都不可用时才启用。这个优先级不能搞反。

07关键失败场景与应对矩阵

区分两类失败很重要：系统故障（要重试/修复）和数据缺失（要记录/跳过）。把后者当故障重试是浪费时间，把前者当缺失跳过会静默丢数据。

页面版本指纹：一个便宜但极有用的机制

录制时，对页面的 DOM 骨架算一个哈希（比如：把关键容器下的标签结构、class 集合、元素数量拼成字符串再 hash）。每次执行前重算一次，与录制时比对。变了就说明页面改版——此时继续跑只会产生一堆错图，正确做法是立刻停下告警，让人来重新录一次。

这比"等截图相似度全部掉下来才发现"要早得多，也便宜得多。建议同时配一个每周一次的冒烟任务：拿 2~3 个已知车型跑一遍，只验指纹和相似度，不改任何产物——这是检测静默改版最省事的手段。

命名规则

# 实际产出示例：
output/final/比亚迪/BYD-宋PLUS-EV/黑色-米色/比亚迪_宋PLUS-EV_黑色-米色_中控正视_01.png

# 清洗规则：空格→连字符，非法字符剔除，中文品牌保留英文别名便于检索

sequence:
  width: 2              # 01, 02 ...
  scope: [brand, series, color, view_id]
  on_conflict: increment

两级去重

第一级 · 快筛
pHash 感知哈希
对缩放、轻微压缩、亮度变化不敏感。汉明距离 ≤ 4 视为同一张。O(1) 比对，适合全库扫描。
第二级 · 确认
SHA256 内容哈希
精确判重。先 pHash 缩小候选集，再 SHA256 确认，兼顾速度与准确。

断点续跑的状态机

pending ──→ running ──→ done
               │
               ├──→ skipped   （数据缺失，如无此配色，不重试）
               │
               └──→ failed    （系统故障，可重试 ≤3 次）

重启时：
  done     → 跳过（不重复劳动）
  running  → 重置为 pending（上次跑到一半，重排队）
  failed   → 若 retry 次数 < 3，重排队；否则留在失败清单等人工
  skipped  → 默认跳过，可用 --retry-skipped 强制重探
两个容易被忽视的工程细节

lock 文件。不加锁的话，两个终端同时跑会各自写 manifest，状态互相覆盖，最后数据一团乱。

侧车元数据。每张图配一个同名 .json，记录来源 URL、抓取时间、机位、camera 数值、相似度、视口与 DPR、授权编号。这既是溯源需要（合规），也是日后发现"这批图角度偏了"时能反查原因的唯一依据。

失败清单的字段设计

失败清单不只是"报错列表"，它应该是可直接重放的工单：

run_id, timestamp, brand, series, model_url, color, view_id,
step_id,        # 卡在哪一步
reason,         # 原因码，见 naming.yaml 的 reason_codes
attempts,       # 已重试次数
screenshot_path,# 失败现场截图
suggestion      # 系统建议：改配色名 / 标记无机位 / 人工重录

关于色彩处理的一个专业提醒

auto_level 和 auto_white_balance 默认都关掉了。原因：做 CMF 和材质对比时，你要的恰恰是真实、未被修饰的色彩关系。自动拉伸对比度会让不同批次的图失去可比性——同一块木纹在两张图里被拉成了不同亮度，对比结论就不可信了。这两个开关只在"单张图用于展示"时才考虑打开。

合规风险分析

核心结论：去除站点标识是法律问题，不是技术问题

我的立场很明确——本方案不提供去除水印/标识的具体技术实现。下面说清楚为什么，以及合规的出路在哪。

风险维度等级具体说明
著作权 · 署名权高 360° 看车的全景图与页面整体构成受《著作权法》保护（摄影作品 / 视听作品 / 汇编作品）。去除"汽车之家"标识直接指向署名权这一著作人身权——人身权不可转让、永久保护，即便拿到了使用权也不当然包含去除署名的权利。
权利管理信息高 水印属于典型的"权利管理电子信息"。故意删除或改变这类信息，在著作权法上有独立的责任条款，且往往是认定"故意侵权"的加重情节。
网站用户协议中高 注册或使用站点通常需接受用户协议，其中普遍禁止批量抓取、禁止去除标识、禁止用于商业目的。即便技术上做得到，违约会带来封号、追责风险。
不正当竞争中高 去除来源后对外使用（汇报、提案、对外发布），会造成来源混淆，可能被认定为《反不正当竞争法》下的混淆行为。这在商业场景下风险尤其大。
技术保护措施中 若站点设置了访问控制、反爬机制，规避这些措施本身可能构成独立违法。所以本方案对验证码、403、封 IP 一律采取停止而非对抗策略。
数据抓取合规中 需遵守 robots.txt、控制频率、声明身份、不抓取需登录或付费内容。高频抓取本身可能构成对服务的干扰。

五条合规替代路径（按推荐度排序）

申请官方授权 / 商务合作
最干净的路径。汽车之家有开放平台与内容合作通道，主机厂与经销商体系也有官方素材库。拿到书面授权后，在系统里填入 license_ref，去标识模块才会解锁。授权要写清楚：用途、范围、期限、是否允许去标识。
使用官方素材源
主机厂 press kit、品牌官网新闻中心 / 媒体中心、经销商后台素材库。这些渠道的图本来就是给你用的，且通常提供高分辨率、多角度、无水印版本。做竞品研究时，先问自己"这张图官方有没有公开发过"。
自行拍摄（4S 店 / 车展 / 自有车辆）
作为内饰设计师，这条路径其实最适合你：完全可控、无版权负担、且能按你自己的机位字典拍摄。缺点是需要协调车辆与场地。建议把它作为主力数据源，把网页抓取作为补充。
保留署名的内部研究库
若确需从网页采集，采取保守模式：不去除任何标识、侧车 JSON 完整记录来源 URL 与抓取时间、严格限于内部研究不外发、控制频率与规模。即便如此也要注意——"内部使用"不是免责盾牌，商业目的的内部研究仍需谨慎。
采购第三方图库
视觉中国、IC photo、以及各主机厂官方图库。适合需要对外发布的场景，授权清晰、可追溯。成本可控，且省下的时间也是钱。
给你的一条实操建议

把"去标识"这个需求重新表述一下，可能问题就消失了。你真正要的大概率不是"去掉汽车之家几个字"，而是"一张干净、没有干扰元素、能放进对比版面的内饰图"。

这个需求有合规的解法：通过构图裁剪把标识区域排除在外（mode: crop_out），而不是像素级擦除。多数水印在角落，而你的机位裁剪区域本来就不一定需要包含角落。这样既得到了干净画面，又完整保留了图片本身——这在合规上和"擦除"是两个性质完全不同的动作。

10分阶段实现路线

核心原则：每个阶段都有可验收的产出，每个阶段都可以停下来。不要试图一次做完——P0 的结论可能会推翻后面所有的工作量估算。

阶段目标做什么验收标准
P0
先做		 可行性探测 不写代码。手工打开 2~3 个车型页，用浏览器控制台回答四个问题：① window 上能不能找到 camera 对象？② 机位是预设按钮还是只能拖拽？③ 全景加载要多久、有没有稳定判据？④ 同一机位连截 3 次，像素是否完全一致？ 产出一份《可行性结论》：明确 L0/L1/L2 哪条通道可用，据此给出后续工作量估算。这一步的结论可能让工程量差 5 倍
P1 单车型跑通 实现 Recorder + Abstractor（可先半自动：录制原始轨迹，人工辅助整理成 task.yaml）。实现 Runner 的单步执行 + 显式等待。实现 Aligner 视觉伺服。实现截图 + 相似度校验。 1 个车型 × 3 个配色 × 8 个机位 = 24 张图，人工验收全部通过。同一任务连跑 3 次，结果 pHash 距离 ≤ 4

P3 后处理与命名 实现可插拔流水线：裁剪、缩放、色彩归一、质量分级、导出。接 naming.yaml 的命名、去重、侧车元数据。实现合规闸门。 成品图命名规范、目录清晰、无重复；质量分级准确（抽样 50 张人工核对）；未授权时去标识模块确实无法启用

关于投入的一个现实提醒

如果你没有工程资源，P1 之前的投入主要在你的时间上——机位字典的定义、基准图的拍摄与验收，这些只有你能做。工程实现（P1~P3）在 P0 结论清晰的前提下，一个有经验的开发者大约 2~3 周能做出可用版本。

但更现实的选择可能是：先只做 P0 + 机位字典，用半自动方式（人工操作 + 简单脚本批量截图）跑通前 50 个车型，验证这套方法论对你到底有没有用，再决定是否投入工程化。工具是为方法论服务的，别反过来。

11技术难点排序

难点 1 · 最高
视角是隐藏状态
360 全景的视角不在 DOM 里，无法用常规选择器校验。必须靠 camera 对象读取或像素比对，而后者本身就有精度上限。这是与普通网页自动化最本质的差别，也决定了方案复杂度。
缓解：P0 阶段优先确认 L0 通道是否可用，若可用难度直接降一个数量级。
难点 2
WebGL 截图的确定性
抗锯齿抖动、渲染时序、加载进度条、鼠标 hover 高亮、动态元素都会让"同一机位的两次截图"产生差异。差异一大，相似度校验就失去意义。
缓解：锁死 DPR/视口/色彩配置、暂停动画、隐藏动态元素、鼠标移出画面、必要时连拍 3 帧取中位。
难点 3
相似度阈值标定
不同机位纹理丰富度差异极大（中控按键多 vs 顶棚纯色），全局一个阈值必然顾此失彼。
缓解：逐机位标定——同机位重复截 10 次得类内方差，不同机位互比得类间方差，阈值取两者之间，写进 views.yaml。
难点 4
选择器漂移与改版
页面改版后所有选择器可能同时失效，且往往是静默发生的。
缓解：4 层候选选择器 + 视觉锚点兜底 + 页面版本指纹提前预警 + 每周冒烟任务。
难点 5
全景加载时间不确定
切片数量多、CDN 波动，加载时间从 3 秒到 40 秒都有可能。固定等待不是太短就是太慢。
缓解：帧稳定判定（连续 N 帧差异小于阈值）作为唯一可靠判据，配合进度条消失检测。
难点 6
并发下的 WebGL 资源上限
浏览器同时活跃的 WebGL 上下文有限（通常 8~16），超了会集体崩溃，且崩溃方式很隐蔽（黑屏而非报错）。
缓解：并发严格 ≤ 4，崩溃时优先怀疑并发数而非代码 bug。
难点 7
组合爆炸
300 车型 × 3 配色 × 8 机位 = 7200 张。全量重跑代价极高，增量策略与去重必须在一开始就设计好，不能事后补。
缓解：manifest 状态库 + 内容哈希去重 + 只跑新增/变更车型。
难点 8 · 隐性
基线本身会过期
基准图是"黄金样本"，但站点可能调整渲染参数、换全景源、改光照——此时基准图本身就过时了，系统会把所有正常截图判为不合格。
缓解：基准图带版本号与生成日期，冒烟任务定期复验基准图有效性。

12验收指标与技术选型

四个可量化的验收指标

技术选型建议

环节选型理由
浏览器自动化Playwright（Python 或 Node）比 Selenium 的选择器引擎更现代，原生支持多候选、自动等待、trace 录制；CDP 直连方便注入 camera 探测脚本
图像处理OpenCV + Pillow / scikit-imageORB 特征、RANSAC 单应、SSIM、pHash 一站式；Python 生态成熟
相似度SSIM + pHash 双指标SSIM 敏感于结构差异（角度偏了会明显掉），pHash 抗压缩噪声（判重用）。两者互补，不要只用一个
状态存储SQLite单文件、零运维、支持并发锁，做 manifest 和断点续跑够用了
配置YAML + CSVYAML 可读性好、支持注释（配置要给人看）；车型清单用 CSV 便于在表格软件里编辑
调度内置队列即可规模在千级任务以内，不需要 Celery / Airflow 这套重武器，徒增运维负担
运行环境headed + 锁定的固定机器WebGL 在无头模式下容易出问题；固定机器保证 DPR、色彩配置、显卡驱动一致，这是截图可复现的前提
最后一句

这套系统里，工程负责"忠实执行"，你负责"定义什么是对的"。机位字典写得有多专业，产出的图库就有多专业——反过来，机位字典如果随便定几个角度，那这套系统做得再完美，也只是高效地生产一堆没法对比的图。

建议顺序：先花时间把机位字典和基准图做扎实，再谈自动化。
